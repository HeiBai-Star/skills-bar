# 仓库、发布与下载

## 识别项目契约

使用用户提供或当前项目确认的仓库。核对 owner/repository、分支、远程、可见性和工作区改动；不要把旧对话的本机路径、默认分支或运行编号当成当前状态。

设计阶段已经确认本次制作后自动发布及目标仓库时，沿用该授权执行，不在推送前重复征求相同范围的许可。配置的默认仓库只决定去哪里，不意味着用户每次讨论或提供新附件都在要求发布。需要宿主权限批准时遵循环境要求，不绕过实际权限限制。

已有仓库遵循其 AGENTS.md 与维护工具。只在普通项目创建一个 Skill 时，不顺便新建远程仓库、插件市场或整套 CI。用户要求多技能仓库时，再建立独立 skills/<name>/ 目录、根目录说明、选定许可和匹配维护需求的检查/打包流程。

重命名或可见性变更需对应授权；完成后核对实际状态，更新本次涉及的远程地址、目录链接和配置，不能靠旧地址可能重定向就声称迁移完成。

## 复用维护工具

阅读脚本及用法，确认属于当前仓库后再运行。若项目实际提供下列工具，可按依赖顺序执行：

~~~text
python scripts/validate_skills.py
python scripts/build_skills.py --package
python scripts/build_skills.py --check
python -m unittest discover -s tests -v
~~~

这些是适用时的仓库命令，不是安装本 Skill 后必然存在的脚本。Python 不可用或缺依赖时，查找宿主运行时与项目依赖；不要将个人虚拟环境路径写成通用方案，或为一次检查修改全局环境。

有生成器时，目录表、索引、摘要和导入链接由生成器维护。内容变化后按仓库约定维护版本，不只改索引中的版本。打包结果是否入库服从既有约定，避免提交无关生成目录。

## 发布闭环

1. 检查改动和未跟踪文件，保护用户已有修改。仅暂存本次所需文件，检查暂存差异；首次新增文件也在这一步完整检查。
2. 核对远程是否前进。遇并发更新，理解差异后安全整合，不强制推送或丢弃本地修改来“保持一致”。
3. 已获发布授权时提交、推送并记录实际提交标识。尚未覆盖发布时，交付可审查本地成品并提出该项选择；等待不等于同意。
4. 查找对应本次提交、分支和工作流的 CI，不能拿旧绿色运行当本次成功。合理间隔检查；失败则看实际任务日志，修复相关问题并重新验证。
5. 核对远程提交、成功任务及产物。不能验证的部分标明目前状态，不把排队或本地成功写成远程全部通过。

认证、网络或权限错误按明确原因选择现有授权渠道。不要盲目重复重试、显示令牌，或通过取消测试绕过失败。

## 给可用的下载入口

| 入口 | 内容与使用方式 |
|---|---|
| 仓库子目录链接 | 用于能够完整获取目录的导入器；确认分支和路径真实存在 |
| Actions 产物 | 下载通常需要 GitHub 登录和仓库读取权限；检查对应运行、保留期限和是否过期 |
| Release 附件 | 实际创建并上传后才能提供链接；增加长期 Release 分发按任务决定 |

[GitHub 产物文档](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)说明下载权限和过期机制。保留天数取自当前配置或产物，不把某次仓库设置当统一规则。不猜资产 ID，不声称尚未创建的 Release 存在。

合集常有两层：解开外层平台产物，再选其中一个 skill-name-version.zip 导入。Code → Download ZIP 是仓库源码包，不自动等于单技能安装包。平台名不同也不能仅凭名称断言内部内容相同；必要时比较清单与摘要。

用户要“最新包”时，核对最新提交和最近成功打包是否一致。最新提交失败时，明确可下载包落后到哪个成功版本。链接过期时提供真实存在的替代产物，或按授权重新打包。
