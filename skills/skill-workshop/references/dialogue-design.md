# 对话设计与方案确认

## 从一个真实用途开始

用户只有一个想法时，先了解他们希望在什么场景得到什么帮助。用已有对话和材料减少提问；每轮优先处理最影响结果的少数问题，不一口气要求填写完整规格。

可以从“你最希望它替你完成哪件事？举一个实际使用场景”开始。已给出场景时，直接讨论其中的关键取舍，例如直接给答案还是先引导、一次交付还是长期续用。需要建议时给出推荐和理由，不让用户替你决定内部文件布局。

目标是共创工作方法，而不是把每个愿望都列为功能。区分现在必需、以后可加和明确不做；功能互相冲突时解释影响，请用户决定实质取舍。不要为了“更智能”擅自增加联网、长期记忆、通知或外部发布。

## 讨论中维护设计稿

用简短的当前结论承接下一轮，不反复从头采访。以下信息足以实施即可，不要求每项单独提问：

- **定位与触发**：帮助谁解决什么问题，哪些请求应使用，哪些不应使用。
- **输入与输出**：用户提供什么，资料不足怎么办，得到什么可用结果。
- **核心功能与顺序**：正常流程、关键判断和必要分支；功能外的事项也写清楚。
- **交互方式**：什么时候解释、提问、练习、直接回答或等待确认；尊重用户临时改变方式。
- **资源与能力**：是否需要文件、模板、脚本、联网或持久记录，哪些依赖可降级。
- **验收场景**：选取能区分好坏的真实请求，说明如何判断达到目的。
- **交付范围**：只制作、安装到指定位置，或制作后发布；发布时包括目标仓库和已知可见性。

技术细节能自行合理确定就不增加问题。示例不是强制功能清单，单一用途的技能可以很短。提供的案例、笔记和聊天记录是设计输入，不默认全部随包公开。

## 何时进入实施

需求尚模糊或用户明确说“先聊聊”，停留在设计阶段；不要生成正式技能文件、提交或推送。可以读取相关材料和规则，形成可修改的方案。

方案足够清楚后，用用户能理解的语言集中概括功能、关键交互、边界和交付目标，请用户确认或调整。发布范围应在这次确认中一起说明，避免之后逐项重复询问。

用户认可当前明确方案且要求制作时，进入实施。肯定回复按其紧接着的方案解释；若上一轮只是列出互斥选项或有未决关键取舍，不把一个“好”扩展为对全部选项的授权。

用户一开始就给出了清晰、完整的需求并要求直接制作或发布，可以简短复述理解后执行，不人为增加一轮确认。已有批准方案也不需要每次重新开题。用户只要讨论、审查或解释时，不因此开始实际制作。

## 已确认后持续推进

实现阶段将设计稿作为验收依据，完成制作、资源整理、验证和已授权的发布，而不停止在“我可以做”或再次问“是否继续”。技术性小修、格式调整和相关验证失败的修复在原范围内自行完成。

已确定本次“制作后自动发布”及目标仓库时，检查和打包通过后直接完成提交、推送与对应提交的 CI 验证。不把相同范围的推送再次变成审批关卡；必要的宿主权限批准仍按环境要求处理。

用户中途提出改动时，先判断影响：小调整直接纳入；改变目标、核心流程、隐私范围或发布位置时，说明差异，只确认发生变化的关键部分。用户说“先别发布”时，保留制作和验证成果，停止发布步骤。

## 续接与能力限制

继续已有任务时，读取最近确认的方案、相关产物和实际仓库状态，区分已完成、待完成和后来变更，不把旧草稿或旧 CI 当最终版本。必要的工作记录留在项目工作区，不混入公开技能包；若需要新建持久记录，遵循用户和项目约定。

Skill 提供流程，不自行获得工具或账号权限。当前宿主缺少写文件、运行命令或 GitHub 访问能力时，仍交付能够完成的设计与文件内容，并指出具体缺口；不要把操作建议描述成实际已发布。
